## Consent (parked 2026-10-04, not yet in GLOSSARY.md)

Shah decided to leave consent out of the glossary for now.

**Settled by Shah:** combined consent is **deprecated**.

**Still open:** is consent a patient filter, a declared planned use, or both? Shah has not answered.

**Findings to build on:**

- The local Elasticsearch `ontology` index holds 124 individual consent entries: context code `Einwilligung`, system `fdpg.mii.cds`, all selectable leaves with no children. They use the MII provision code system (`urn:oid:2.16.840.1.113883.3.1937.777.24.5.3`). Only `name` is filled in; `display.de` and `display.en` are empty.
- Combined consent (code system `fdpg.consent.combined`, 16 codes such as `yes-yes-no-yes`) is generated by `fhir-ontology-generator` (`projects/fdpg-ontology/combined_consent_generation.py`) from a CSV. Each code expands to a fixed set of the individual provisions. The local index has no combined entries (0 hits), probably because the combined tree is merged separately.
- The UI mirrors the 16 combinations in `src/app/service/Consent/Consent.service.ts`. The toggle is currently disabled.
- Backend: `CcdlValidator` skips the term-code existence check for `fdpg.consent.combined`, and the query translator aliases it to `fdpgcombinedconsent`.
- TORCH changelog: combined consent keys are no longer supported in the CRTDL and are not expanded. Consent keys must be individual MII OID provision codes. So combined consent still works for feasibility queries but not for data extraction.

**Draft glossary terms, if confirmed:**

- *Consent provision*: one specific permission a patient granted or denied, as defined by the Medical Informatics Initiative; selectable as a criterion.
- *Combined consent*: deprecated shorthand for a fixed bundle of provisions chosen via four yes/no questions (distributed analysis, EU-GDPR, insurance data, re-contact).

**Possible code issues (not ticketed):** the UI still builds combined consent keys; typo "Krankenassendaten" in `Consent.service.ts`.
